# Technology Decision Log — Drug Interaction Safety Assistant

Every external dependency (library, service, engine) the project takes on gets a row here, added when it's introduced — not batched up later. Entries carrying real environment risk (native dependencies, competing engines, ML runtimes) include what was actually tested, not just the conclusion.

| **Neo4j** (Community Edition) | 5.24 | Primary graph database (SD-007) | ArangoDB, Memgraph, `kuzu` (embedded) | **Spiked, not guessed** (Build Plan V0.1): ran Neo4j in Docker, connected via the official Node driver, applied a real `IS UNIQUE` constraint, did a live write + read round trip — all passed. Also tried `kuzu`, an embedded/no-Docker option, specifically to see if it would avoid the Docker Desktop dependency; rejected because the npm package is marked deprecated upstream and its install pulls in `node-tar` (via `cmake-js`) with a critical-severity advisory (`npm audit`: 2 high, 1 critical, no fix available). ArangoDB/Memgraph weren't spiked — Neo4j's spike succeeded cleanly on the first try with no environment friction, so the comparison stopped there rather than spiking alternatives with no open problem to solve. **Update (V0.3):** confirmed live that Community Edition (not just Enterprise) supports **relationship-property** uniqueness constraints (`FOR ()-[r:INTERACTS_WITH]-() REQUIRE r.id IS UNIQUE`), not only node-property ones — worth having verified rather than assumed, since several competing graph engines gate relationship constraints behind an Enterprise/paid tier. | 2026-08-17 |

| **Cytoscape.js** | ^3.34.1 | Graph rendering for SCR-004 (risk relationship-path visualization) | `react-force-graph`, `vis-network` | **Spiked, not guessed** (Build Plan V0.6): checked dependency health first — `react-force-graph` pulls a **git+ssh dependency** (`three-bmfont-text`, transitively via `aframe`/`3d-force-graph-vr`, because the package bundles 2D/3D/VR/AR variants together) — a real installability risk for VR capability this project never needs, so it was eliminated without benchmarking, same reasoning as rejecting `kuzu` in V0.1. Benchmarked cytoscape vs. vis-network headless at 50 synthetic nodes: both blew the NFR-002 1s budget with default physics-based layouts (~1200ms each). Switched both to non-physics layouts suited to a small tree-shaped path (what this product actually renders, never an arbitrary dense graph): cytoscape `breadthfirst` ≈189ms, `grid` ≈93ms; vis-network with physics off ≈252ms — all comfortably under budget once given the right layout mode. Chose cytoscape: 6MB install vs. vis-network's 81MB (the latter ships several redundant prebuilt bundle variants inside the package itself), npm-registry-only dependency chain, and purpose-built for typed relationship graphs like this one. | 2026-08-17 |
| **Vitest** (apps/web) | ^2.0.5 | Unit-testing the graph domain rule and use case (`apps/web/src/graph`) | — | First real use in the web workspace (already decided in System Architecture §6, same as the API's Vitest entry above). Wired via `vitest/config`'s `defineConfig` merged into `vite.config.ts`. 9 tests, zero DOM/network dependency. | 2026-08-17 |
| **multer** | ^2.2.0 | Multipart file upload parsing for `POST /admin/import` (SD-006) | Express's own body parser (no multipart support at all) | Standard, low-risk choice — the de facto Express multipart middleware, on its current major (v2, post the v1.x CVEs). Checked `npm view` for deprecation (none) and did a scratch install to confirm zero vulnerabilities and no native dependency before adopting; no full spike, since there's no competing-engine or native-runtime risk here to spike against. Configured with `memoryStorage()` (file only needs to be parsed once, not persisted to disk) and a 5MB size limit. | 2026-08-17 |
| **csv-parse** | ^7.0.2 | CSV parsing for the drug bulk-import pipeline (SD-006) | Hand-rolled `.split(",")` parsing (rejected — breaks on quoted fields, embedded commas) | Same low-risk category as multer: part of the well-established `node-csv` project, ships its own TypeScript types, zero vulnerabilities on a scratch install, no native dependency. Used the synchronous API (`csv-parse/sync`) — the whole file is read into memory and parsed once per import, not streamed, which fits this project's demo-scale CSVs and keeps the import pipeline's code simple. | 2026-08-17 |
| **jsPDF** | ^4.2.1 | Client-side PDF rendering for the Export Report feature (`apps/web/src/export/pdfRenderer.ts`), replacing the original JSON-only export | `pdfmake` (heavier, ships its own bundled fonts), browser `window.print()` (rejected — changes the UX from a direct file download, proven live in V0.11's original check, to a print-dialog flow, and doesn't reliably produce a saved file the same way) | Pure JS, no native binary, MIT-licensed, ships its own TypeScript types — same low-risk category as multer/csv-parse, no competing-engine spike needed. Used only for programmatic text/line drawing (title, severity-colored paragraphs); no image/font embedding. Severity colors are hand-copied hex values matching `styles.css`'s tokens, same pattern already established for Cytoscape in `GraphView.tsx`, since a PDF canvas can't read CSS custom properties either. | 2026-08-19 |
| **openai** | ^7.5.0 | LLM entity extraction + natural-language answer composition for the conversational interface (SD-009, Build Plan V2.0) | Anthropic (`@anthropic-ai/sdk`) | **Reverses the V0.5 decision** ("Template-based string generation, no LLM... AI Architecture was explicitly skipped") — done deliberately, not accidentally, at the user's explicit direction for the v2 conversational redesign. User chose OpenAI over Anthropic despite this build running inside a Claude Code session. The exact current model id should be confirmed against OpenAI's live model list at implementation time rather than hardcoded from training data (same "don't guess" discipline as every native-dependency row above). Scope is deliberately narrow: the LLM only extracts entity names/intent from free text and rephrases an already-graph-grounded fact set into prose — it never gains direct graph query authority, and `checkRisks`/`assertGroundedInPath` (V0.3–V0.5) are unchanged. See `docs/v2-conversational-assistant/05-system-architecture.md` §6 and `02-requirements.md` REQ-028/029 for the grounding contract this constrains it to. | 2026-08-21 |

| **react-markdown** | ^10.1.0 | Renders assistant reply text as markdown (bold/lists/paragraphs) instead of a raw string (improvements.md #2.6, Build Plan V2.2.5) | `marked` + `dompurify` (HTML-string sanitization), a hand-rolled regex renderer | Chosen specifically to avoid `dangerouslySetInnerHTML` altogether: it parses markdown into React elements directly rather than an HTML string, so there's no injected-HTML/XSS surface to sanitize in the first place, unlike the `marked`+`dompurify` pairing which still requires get-the-sanitizer-config-right diligence on every LLM-produced string rendered. No native dependency, MIT-licensed, ESM-only (fine — Vite handles ESM natively). Used with its default (safe) element set — no `rehype-raw` plugin, which is what would reintroduce raw-HTML rendering and the injection risk this choice exists to avoid. | 2026-08-23 |
